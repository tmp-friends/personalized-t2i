01論文の中身

同じ「a cat」でも、猫の写真ばかり作ってきた人とアニメ塗りばかり作ってきた人では欲しい絵が違う。Tailored Visions は生成モデルを一切触らず、ユーザの過去プロンプト履歴を検索して LLM に渡し、プロンプトを書き換えることでこれを解く。

著者は Chen Zijie ほか (Westlake University)。自前の text-to-image サービスから収集した PIP (Personalized Image-Prompt) データセット（3,115 ユーザ / 300,237 プロンプト）を同時に公開している。

パイプライン

3 段。下段は実際にこのマシンで動かした出力（ユーザ 100440、BM25 検索）。

STAGE 1Retriever

現在のクエリに近い履歴プロンプトを top-k 件取る。EBR（CLIP ViT-L/14 のテキスト埋め込みで cosine 類似度）か BM25。論文の既定は k=3。

query: Women's jacket with rich color scheme and simple style
STAGE 2Rewriter

検索した履歴を「このユーザの好み」の証拠として ChatGPT に渡し、書き換えさせる。デモ例を 1 件付ける 1-shot ICL が最良。

retrieved (BM25): 12.62 Women's clothes with a nice color scheme … artstation 6.71 A woman wears a white jacket … loose pants … artstation 5.66 jacket for women … artstation
STAGE 3T2I

書き換え後のプロンプトを Stable Diffusion v1-5 に投げる。PNDM スケジューラ / 50 steps / CFG 7.0。

rewritten: A woman wears a women's jacket with a rich color scheme and simple style. The jacket features a nice color palette trending in artstation, paired with a simple inner layer and loose pants. …

履歴に trending in artstation が頻出する → 書き換え後にもそれが入る。これが「嗜好の反映」の実体。

書き換え指示文（論文 Table 1・逐語）

手法の中核はこの 2 文だけ。official/prompts.py の Example_template にそのまま入っている。

Prompt in text-to-image generation describes the detailed attributes of
the object it plans to draw. User's preference in text-to-image generation
is shown in history prompts.
Given 3 history prompts, your task is to rewrite the current prompt so that
it matches the user's preference. The rewritten prompt should retain primary
objects in the original prompt and conform to the user's preference. Please
avoid being too diffused and restrict your output within 70 words.

1 ユーザ分（train 16 件 / test 2 件）多い。配布ファイルをそのまま使っている。ユーザ 1 人あたり最低 18 枚生成しており、各ユーザから 2 件を test に抜く分割。test のクエリは元プロンプトを ChatGPT で短縮したもの。

評価指標

PMS (Preference Matching Score)
2.5 · max(cos(E(I'u), E(Pu)), 0)
生成画像と「ユーザ嗜好 Pu」（履歴を ChatGPT で 5 フレーズに要約したもの）の CLIPScore。
Image-Align
cos(E(I'u), E(Igt))
生成画像と、ユーザが実際に保存した画像の CLIP 画像間類似度。
ROUGE-L (β=5)
rewritten vs. 元の完全プロンプト
β=5 で recall 寄り。書き換えが元プロンプトをどれだけ復元できたか。

画像系 2 指標は CLIP ViT-B/32、検索側の EBR は ViT-L/14 と、使い分けている。

アブレーション

  • 検索件数 k（Table 4, EBR + 1-shot）: k=3 が ROUGE-L 0.4686 で最良。k を増やすと冗長な履歴が混ざり、入力も長くなって悪化。
  • ICL のデモ数（Table 5）: 1-shot が最良。3, 5 と増やしても改善しない。
  • 入力の短さ（Table 3）: Noun / Noun Phrase / Short Sentence の 3 段階すべてでベースラインを上回る。名詞だけの入力でも ROUGE-L 0.1770 → 0.2804。

オンライン評価

自社サービス上でのシングルブラインド。247 ユーザが 905 枚生成（元プロンプト 433 / 書き換え後 472）、ユーザの「保存」操作を指標にして Save 率 +17.1%。オフライン指標より説得力があるのはこちら。

03今回やったこと

公式コードは配布状態では 1 行も動かない

main.py が MY_BASE を import しておらず、あらゆる実行が起動直後に NameError で落ちる。それ以外にも実行を止めるバグが 6 件、結果を静かに間違えるバグが 4 件あった。

公式リポジトリ（zzjchen/Tailored-Visions @ d0f4454）をそのまま clone し、2026 年の環境で動くところまで持っていった。上流との差分は全て git に残してあり、各所に [2026 patch] コメントを付けてある。

ChatGPT なしで動かせるようにした

上流は書き換えを ChatGPT に投げる設計で、API キーがないと何も確認できない。同じ /v1/chat/completions を喋るローカルサーバ（serve_local_llm.py, Qwen3.5-4B）を足して、向き先を差し替えるだけで動くようにした。apiuse.py の呼び出し経路は上流のまま。

  • リクエストは 50ms 単位でまとめてバッチ推論する。main.py は 1 件ずつ投げてくるので、これがないと 6,232 サンプルが現実的な時間で終わらない。
  • Qwen3.5 は既定で <think> ブロックを出す。書き換え結果に混入すると全指標が静かに壊れるので enable_thinking=False を指定。

論文の数値を再現したいならローカル LLM は使わないこと。書き換えモデルは手法そのものなので、モデルを替えれば数値は変わる。OpenAI のキーがあるなら環境変数を差し替えるだけでそちらに向く（§05）。

05起動方法

run.sh がローカル LLM サーバの起動込みで面倒を見る。ターミナル 1 つで完結する。

基本

cd ~/stable-diffusion/personalized-t2i/tailored-visions-repro/official

# 書き換え + 画像2枚（ori_prompt.png / personalized_prompt.png）
./run.sh demo 'a cat'

# 書き換えのみ・数秒（SD をロードしない）
./run.sh demo 'a cat' --no-t2i

# PIP データセットで実験。まず 5 ユーザで様子を見る
./run.sh main --limit_users=5
./run.sh main --limit_users=5 --t2i
#   -> image_result/<日時>/<user>-<query>-<n>/ に ori.png, generated.png, result.txt

# 全 3,116 ユーザ（--limit_users を省略）。--t2i 付きだと数日かかる
./run.sh main

# ローカル LLM サーバを止める（VRAM 約 9GB を解放）
./run.sh stop

run.sh が起動する LLM サーバは nohup でバックグラウンドに残る。他の用途で GPU を使う前に ./run.sh stop すること。認証はなく 127.0.0.1 のみに bind しているが、同じマシンの他ユーザからは叩ける。

08分かったこと

1. テストセットの約 1/3 が学習履歴にリークしている

ROUGE-L は「元プロンプトをどれだけ復元できたか」を測る。ところが正解プロンプトがそのまま同一ユーザの履歴に入っているなら、検索がそれを引いてくるだけで点が取れてしまう。全 6,232 テストサンプルに対して：

履歴に token-F1 ≥ 0.8 のプロンプトが存在49.1% · 3,062
正解プロンプトが生の履歴に完全一致35.6% · 2,217
同上（重複除去後＝実際に検索される履歴）31.3% · 1,948
クエリ自体が正解プロンプトと同一18.2% · 1,135
0%25%50%

最後の 18.2% はデータ生成の副作用。data_process.py は 6 語以下のプロンプトを短縮しないので、短いプロンプトはクエリ＝正解になり、何もしないベースラインが満点を取る。

結果として ROUGE-L は履歴を参照する手法を構造的に過大評価する。06_evaluate.py はリーク除外後の列を必ず併記するようにした。これは公開データセット側の性質で、再現実装の問題ではない。

2. モデルを使わないベースライン行が論文と一致しない

Shortened Prompt: 0.3964（実測） vs 0.3268（論文）

この行は入力プロンプトをそのまま使うだけで、LLM も画像生成も介在しない。データと指標設定だけで決まるので、本来は完全一致するはず。一致しないということは、論文の ROUGE-L の前処理が公開物からは復元できないことを意味する。

前処理の候補（小文字化、preprocess_line 適用、β の違い）を総当たりしたが、0.3268 を再現する組み合わせは見つからなかった。したがって絶対値の比較はできない。ベースラインからの差分で比較する必要があり、06_evaluate.py は Δ 列を出すようにしてある。

3. ROUGE-L の実装が長い書き換えに有利

公式の rougeL は文字列を "." で分割してから summary-level LCS を取る。正解プロンプトはカンマ区切りの断片が多く、書き換え結果は普通の文章なので、この非対称性が効く。実測：

  • 4 語のベースライン（shortened_prompt）: +0.0002
  • 53 語・96% が複数文の書き換え（general_pr）: +0.0163

手法と相関するバイアスなので、RESULTS.md に 1 セグメント版（1-seg 列）も併記している。既定は論文の数値を生んだ実装のまま。
